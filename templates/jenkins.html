Agent8 for Jenkins

Run Jenkins agents on hosts stuck on Java 8, 11 or 17.

Jenkins now requires Java 21 on the controller and on every agent. With Agent8 the controller moves on, and the old build host keeps its Java and stays an ordinary node.

Install

One script, plain sh, any old Unix

1

It asks your controller

install.sh reads the remoting version of the controller's agent.jar and downloads the Agent8 release built for it, in the build for the host's Java. If there is none yet, it says so and uses the latest release.

2

It checks before it swaps

Downloads are checked against sha256sums.txt and test-started on the local Java. The old jar is kept, and --restore puts it back.

3

You restart as usual

Same java -jar command, same service script. Offline hosts copy the jars and sha256sums.txt and use --from DIR; fleets use the Ansible playbook.

Questions teams ask first

Is this an official Jenkins project?

No. Agent8 is independent and not endorsed or supported by the Jenkins project. Report problems on its GitHub issues, not the Jenkins tracker.

Why not run agent.jar on Java 21 and build with the old JDK?

If the host can install Java 21, do exactly that: the agent's Java and the build's Java are separate, and you don't need Agent8. Agent8 is for hosts that can't: AIX 7.1, HP-UX on Itanium, Solaris 10, and hosts where nothing new may be installed. The usual workaround there, copying the workspace over with scp and building over ssh, struggles with parallel builds and aborts; with Agent8 the host is an ordinary node.

Why not run the build in a container?

That works for many RHEL 6 builds, and RHEL 6 x86_64 hosts can also install Amazon Corretto 21 or Azul Zulu 21 and run the stock agent. Neither covers builds that must run natively on AIX, Solaris or HP-UX hardware.

Does any controller setting matter?

Only if the Versions Node Monitors plugin (versioncolumn) is installed. Its JVM Version monitor takes Agent8 nodes offline seconds after they connect, so set it not to disconnect. Its Remoting Version monitor does the same when the agent's build differs from the controller's. The README has the configuration-as-code snippet.

What happens when we upgrade the controller?

Rerun install.sh (or the playbook) and restart the agent. Jenkins refuses agents older than a minimum remoting version that it raises over time: Jenkins 2.586 already refuses the Agent8 build for 2.462.3.

What hasn't been tested yet?

Builds on real Solaris and HP-UX; real AIX hosts; plugins that run their own code on the agent beyond Git checkout (JGit) and credentials, such as Maven or Docker; and the Maven project type. The README keeps the list.

Which launch methods work?

Inbound agents, started with java -jar agent.jar, and the SSH Build Agents launcher: set the node's Java Path to the java file install.sh writes, and it runs Agent8 instead of the stock jar the launcher copies.

What is the license?

Agent8's own code is MIT. Its jars also contain Jenkins remoting (MIT), ASM (BSD-3-Clause) and JvmDowngrader classes (LGPL-2.1), and each release ships JvmDowngrader itself as jvmdg.jar (LGPL-2.1, unmodified).
